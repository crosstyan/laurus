# Field report — first LOS 24 boot on the CC9e (2026-10-25)

Status: **succeeded on the third flash attempt.** This is the observed sequence from Claude
Code session `bd6da2a0-2ae3-4e72-ba1c-1836c8886a73`. It separates what was measured from
what is inferred; the two failed attempts were not the same failure.

- Host: Mac (`ssh <lan-ip>`); this abl never enumerates fastboot on the Linux
  workstation.
- Device: CC9e `laurus`, A-only, unlocked, TWRP 3.3.1 on `recovery`, A9 firmware untouched.
- Target: LOS 24 `laurel_sprout` nightly 20261020 (`system`, `vendor`, `dtbo`) plus the
  kernel/vendor graft. Host timestamps below are the Mac's local clock (UTC+8), from
  `logs/losboot-*`.

## Attempts at a glance

| # | boot image (kernel `image_size`) | what happened | root cause |
|---|---|---|---|
| 1 | `boot-laurusdbg-adb-permissive.img` (61.84 MiB `image_size`) | reset at the “unlocked” + Mi logo; no pstore, no adb | kernel in-memory size above the bootloader limit (bracketed: 51.92/51.96 MiB `image_size` boots, 61.84 MiB does not) |
| 2 | `boot-losprebuilt-adb-permissive.img` (51.92 MiB `image_size`) | boot animation, no USB/adb; TWRP could not mount `/metadata`; after that was fixed, boot still hung | two independent blockers: (a) `/metadata` was erased, not ext4; (b) the vendor fstab still had `slotselect`, so the A/B boot-control HAL aborted and vold waited forever |
| 3 | `boot-losprebuilt-adb-permissive.img` (51.92 MiB `image_size`) | setup wizard; `/data` f2fs/FBE, 107 GB; hardware up | metadata formatted ext4; `slotselect` stripped from the vendor fstab; A/B boot-control HAL removed |

The raw 3 GiB `system.img` also failed to flash once (`Failed reading from system`); the
sparse conversion fixed that. That is a fourth, unrelated gotcha (below).

## Attempt 1 — the kernel never ran

Flash sequence, all on the Mac:

```sh
fastboot flash boot   flash/boot-laurusdbg-adb-permissive.img   # custom debug kernel
fastboot flash dtbo   flash/dtbo.img
fastboot flash vendor flash/vendor-laurus.img
fastboot flash system flash/system.img                          # raw 3 GiB
```

The first system flash failed:

```
fastboot: error: Failed reading from system
```

`system.img` is 3,221,225,472 B; the host is `fastboot 37.0.1`, `max-download-size`
805,306,368. `img2simg` produced a 2,050,543,832 B sparse image; `simg2img` + `cmp`
round-tripped it identically, and the sparse image flashed in three chunks.

The sequence then ran:

```sh
fastboot erase userdata
fastboot erase metadata
fastboot erase cache
fastboot reboot
```

Both `erase userdata` and `erase cache` printed `******** Did you mean to fastboot format
this ext4 partition?` — benign here, because Android formats them. `fastboot
getvar partition-type:metadata` had already reported `raw`; that warning was the relevant
one.

Symptom: the phone stayed at the bootloader's “unlocked” + Mi logo, then reset. The watcher
saw `fastboot -> none -> fastboot` and no adb. TWRP came up, but its pstore directory was
empty (`pstore:` printed nothing, `last_kmsg` was 0 B). **No kernel log at all** means the
kernel never started; this is a bootloader-stage failure, not an Android failure.

Cause: the boot image's kernel is too large. The relevant number is the arm64 Image header's
in-memory `image_size` (includes zero-filled BSS), not the compressed file size:

| kernel | `image_size` (MiB) | decompressed (MiB) | result |
|---|---:|---:|---|
| stock laurus (2019) | 34.6 | — | reference |
| LOS prebuilt | 51.92188 | 48.33 | boots |
| BakaSU rc3 | 51.93359 | 48.34 | boots |
| SukiSU | 51.95703 | 48.36 | boots |
| our debug build | **61.83984** | 55.99 | resets at the Mi logo |

The bootloader checks the arm64 Image header `image_size` (which includes BSS), not the file
size and not the decompressed kernel size. The **measured bracket is 51.96 MiB (boots) /
61.84 MiB (resets)**. The 52 MiB window is now **confirmed from the ABL**, not inferred from
the gate: IDA recovered `UpdateBootParams`/`BootLinux` from the compressed ABL PE; see
`notes/abl-bootlinux.md`.

- `/proc/iomem` on a booted kernel shows `Kernel code` starting at `0x40080000`.
- The ABL's 64-bit fallback sets `KernelLoadAddr = BaseMemory | 0x80000` and
  `KernelEndAddr = BaseMemory + 0x3400000`; the source defines
  `KERNEL_64BIT_LOAD_OFFSET 0x80000` and the 32-bit path `0x8000`/`0x3200000` (50 MiB).
- The UEFI-variable path uses `KernelBaseAddr + KernelSize`; the known-good 51.957 MiB
  image ends at `0x43475000`, consistent with `KernelEndAddr = 0x43480000` (52 MiB from the
  kernel load). The XBL "Kernel" memory region is 87 MiB (`0x40000000..0x456fffff`), leaving
  room for the ramdisk/DTB above the kernel window.
- The known-good images end at `0x4346c000` (LOS), `0x4346f000` (BakaSU), `0x43475000`
  (SukiSU) — 44–80 KiB below `0x43480000`. The debug image ends at `0x43e57000`, 9.84 MiB
  over, and resets.

The session's “48.3 MiB” for the LOS kernel was the **decompressed file**, not the header
`image_size`; that is why it looked smaller than the 51.9x known-good builds.

The project's ≤51.96 gate was an arbitrary convention (not evidence), but the ABL's
`0x3400000` 64-bit constant / 52 MiB end confirms the same window. The exact runtime
`KernelSize` UEFI variable is not in the persistent `uefivarstore` dump (XBL sets it at
runtime); the ABL fallback plus the known-good/bad boundary pin it at 52 MiB. Keep a margin
and stay under 48 MiB for new builds.

### Field note — the 44 KiB is not the ABL's margin

The ABL does **not** compare the arm64 Image header `image_size`. Its check is
`KernelLoadAddr + KernelSizeActual > KernelEndAddr`, where `KernelSizeActual` is the
**decompressed kernel blob**, rounded up to a page. For the known-good builds:

| build | `image_size` | decompressed | ABL headroom in 52 MiB |
|---|---:|---:|---:|
| LOS prebuilt | 51.92188 | 48.333 | 3.666 MiB |
| BakaSU rc3 | 51.93359 | 48.341 | 3.658 MiB |
| SukiSU | 51.95703 | 48.355 | 3.644 MiB |
| debug | 61.83984 | 55.990 | **−3.990 MiB** |

So the “44–80 KiB headroom” is only in `image_size`; the ABL’s actual check has ~3.6 MiB
of room for the known-good kernels. The debug is ~4.0 MiB over the ABL check, not 9.84 MiB.
`image_size` includes BSS, which the bootloader does not copy; the ABL checks the
decompressed blob. The 51.96 gate is a conservative proxy, but the real margin is larger.
Still keep the ≤48 MiB target: BSS/memory layout and future config changes can move both
numbers, and a 3.6 MiB margin is not worth gambling on.

Build check: compute **both** the arm64 `image_size` and the decompressed `zlib` length;
fail at 50 MiB (or 48 MiB for margin) for either. `tools/repack_los_boot.py` currently prints
`image_size`; the decompressed length is easy to add.

Fix for bring-up: flash `boot-losprebuilt-adb-permissive.img` (LOS kernel; `image_size`
51.92 MiB).
Later builds stayed under the 52 MiB window (drop DEBUG_INFO/tracing, keep FTRACE — see
`README.md`).

## Attempt 2 — Android started, `/data` never mounted

Flashed the LOS-prebuilt kernel image and rebooted. This time Android's boot animation
appeared, so the kernel, first stage and display stack worked. But **no USB function at
all** appeared (no adb, no fastboot; `system_profiler` saw no Xiaomi/Google device), so the
`force_debuggable` adb override had not taken effect.

To get logs anyway, I built `vendor-laurus-logs.img`: an init service that dumps
logcat/dmesg/props/pstore to `/metadata/laurus-logs`, forces `sys.usb.config=adb`, and
installs the hosts' adb keys. It still produced no USB, but TWRP could now be used as the
fallback. (TWRP's display was blank while its adb worked; that was a separate annoyance,
not a flash problem.)

### 2a. `/metadata` was raw, not ext4

From TWRP's adb shell:

```
mount: mounting /dev/block/by-name/metadata on /mnt/meta failed: Invalid argument
```

The partition was dumped and inspected: 16 MiB, `file` said `data`, the ext4 superblock
magic at offset `0x438` was `0000`, and `tr -d '\0' | wc -c` was `0`. It had only ever been
**erased**; LOS did not recreate the filesystem on this boot.

Formatted from TWRP:

```sh
mke2fs -t ext4 -b 4096 -L metadata /dev/block/by-name/metadata
mount -t ext4 /dev/block/by-name/metadata /mnt/meta && echo METADATA-OK
```

`mke2fs` created 4096 4 KiB blocks (the 16 MiB partition), a 1024-block journal, and the
mount then succeeded.

This matters because the vendor fstab mounts `/metadata` in first stage, and `/data` uses
`keydirectory=/metadata/vold/metadata_encryption`: with a raw metadata partition, vold has
nowhere to put the metadata-encryption keys.

### 2b. `slotselect` in the vendor fstab crashed the boot-control HAL

A reboot after the mke2fs still failed. This time pstore had content
(`console-ramoops-0`, 254,204 B, sha256 `f4009c9c…`). It showed a repeating loop:

```
android.hardware.boot-service.qti: [libfstab] Error updating for slotselect
android.hardware.boot-service.qti: [libfstab] ReadFstabFromFileCommon(): failed to load fstab from : '/vendor/etc/fstab.qcom'
android.hardware.boot-service.qti: [libfstab] ReadDefaultFstab(): failed to find device default fstab
android.hardware.boot-service.qti: Check failed: bootcontrol_init()
DEBUG: Abort message: 'Check failed: bootcontrol_init() '
...
libbinder.ServiceManagerCppClient: Waited one second for android.hardware.boot.IBootControl/default
servicemanager: Caller(pid=625,uid=0,sid=u:r:vold:s0) ... could not be found trying to start it as a lazy AIDL service
```

The LOS vendor's own `/etc/fstab.qcom` still had `slotselect` on five lines:

```
system     wait,slotselect,avb,first_stage_mount
vendor     wait,slotselect,avb,first_stage_mount
bluetooth  wait,slotselect
dsp        wait,slotselect
modem      wait,slotselect
```

This is an A-only phone: the abl passes no `androidboot.slot_suffix`. libfstab refuses the
fstab, `android.hardware.boot-service.qti` aborts in a loop, and vold blocks forever waiting
for `android.hardware.boot.IBootControl`.

`vendor-laurus-fix1.img` (1056714752 B, sha256 `8b8ba2fd…`) removed both vendor-side
problems:

- stripped `slotselect` from those five fstab lines (debugfs; mode/uid/gid/SELinux
  preserved; no other file under `/vendor/etc` mentioned it);
- removed the A/B boot-control HAL: `/etc/init/android.hardware.boot-service.qti.rc` and
  its VINTF fragment (`etc/vintf/manifest/boot-service.qti.xml`).

After flashing fix1 and rebooting, adb appeared at 11:31:55 and `sys.boot_completed=1` at
11:32:52 — the setup wizard.

## Attempt 3 — and the later GApps reflash

The first successful boot was: LOS-prebuilt boot + `vendor-laurus-fix1.img` + metadata
formatted by TWRP's `mke2fs`.

The later GApps flash (SukiSU boot 51.96 MiB + `vendor-laurus-fix3.img` +
`system-gapps.sparse.img`) used the host-side path instead:

```sh
fastboot erase userdata            # LOS formats /data f2fs itself
fastboot format:ext4 metadata      # runs mke2fs on the host
fastboot reboot
```

Output:

```
******** Did you mean to fastboot format this ext4 partition?
Erasing 'userdata' ... OKAY
Warning: metadata type is raw, but ext4 was requested for formatting.
mke2fs 1.47.2 (1-Jan-2025)
Creating filesystem with 4096 4k blocks and 4096 inodes
...
Sending 'metadata' (180 KB) ... OKAY
```

Both warnings are benign: `fastboot getvar partition-type:metadata` reports `raw`, but
`format:ext4` still runs `mke2fs` and writes a valid 16 MiB ext4 image. Boot completed in
~45 s; `/data` was f2fs with FBE.

## Root causes, separated

| failure | evidence | cause | fix |
|---|---|---|---|
| attempt 1 never reached the kernel | empty pstore, no adb, reset at the Mi logo; 61.84 vs 51.92/51.96 MiB `image_size` | kernel in-memory size above the (unknown) abl limit, bracket 51.96–61.84 MiB | stay near the known-good 51.96 MiB or below; 48 MiB for margin |
| boot animation, no USB | no USB device on the host; partition dump all zeros; `mount` returns `EINVAL` | `/metadata` erased, never formatted | `mke2fs -t ext4` (TWRP) or `fastboot format:ext4 metadata` |
| hung after metadata was fixed | pstore: `libfstab` slotselect error → `bootcontrol_init()` abort → vold waits | vendor fstab kept `slotselect`; A/B boot-control HAL present on an A-only device | strip the five fstab flags; remove the HAL rc + VINTF fragment |
| raw system flash error | `Failed reading from system` on a 3 GiB raw image | host fastboot did not accept the raw image as-is (exact reason not established) | `img2simg` first; 2.05 GB sparse flashed |

The first failure was **not** a partition-format problem; the second one was. Both were
needed to get LOS up.

## Checklist for the next first boot (A-only CC9e)

1. **Boot image:** check the kernel's in-memory `image_size` before flashing. 51.96 MiB is
   proven good; 61.84 MiB is known bad; the exact ceiling is unknown between them. 52 MiB
   (`0x3400000`) is a working hypothesis, not a measurement. Aim ≤48 MiB for new builds; the
   repack tool prints `image_size`.
2. **System image:** if the source is a raw ~3 GiB ext4, convert it with `img2simg` before
   `fastboot flash system`.
3. **Metadata:** run `fastboot format:ext4 metadata` (never bare `erase metadata`). If the
   host fastboot lacks `mke2fs`, do it in TWRP:
   `mke2fs -t ext4 -b 4096 -L metadata /dev/block/by-name/metadata`.
4. **Vendor:** strip `slotselect` from `/etc/fstab.qcom` (system, vendor, bluetooth, dsp,
   modem) and remove the `android.hardware.boot-service.qti` rc file plus its VINTF
   fragment. `vendor-laurus-fix1` and later are already fixed.
5. **Boot image fstabs:** `tools/repack_los_boot.py` already strips `slotselect`/`avb` from
   the ramdisk's `first_stage_ramdisk/system/etc/fstab.qcom` and `system/etc/recovery.fstab`.
6. **First boot:** allow ~2.5 minutes; adb may not appear until boot completes. If there is
   no USB, use TWRP and read `/sys/fs/pstore/console-ramoops-0`.
7. **Do not rely on `force_debuggable` on this LOS build:** the override did not activate
   (`ro.debuggable` stayed 0); the vendor log service was the only fallback. It is harmless
   to include it, but it is not a logging guarantee.

## What is automated, and what is not

- `tools/repack_los_boot.py` — automated: v2→v1 header, ramdisk fstab `slotselect`/`avb`
  strip, `force_normal_boot`, optional `--debuggable`/`--permissive`.
- `tools/graft_vendor.py` — automated: audio calibration graft, module replacement, AVB
  footer erase. **Not** automated: the vendor `/etc/fstab.qcom` strip and the boot-control
  HAL removal. `vendor-laurus-fix1` was a manual debugfs edit. If the LOS vendor changes and
  has to be re-grafted, repeat that edit or use a pre-fixed vendor image.
- Metadata formatting is a flash-time step, not an image property; it cannot be baked into
  `system`/`vendor`. Recorded in `README.md` and `PLAN.md`.

Note: `notes/los-upgrade.md` used to claim that `graft_vendor.py` strips `slotselect` and
removes the boot-control HAL. It does not; the sentence was corrected with this report.
